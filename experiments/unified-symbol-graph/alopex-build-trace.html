Build Provenance — Worked Example

alopex-cli の実行可能バイナリを遡る

1本の ELF 実行ファイルから出発し、それが実際にどの主体（Cargo / rustc / LLVM / Nim / リンカ）の、 どの粒度の作業を積み上げて生まれたのかを遡って可視化する。 このセッション中に alopex-cli（LAMINARIA の参照実測対象）を実際にビルドし、 各主体の実コマンド出力を観測した結果にもとづく一例。

00凡例 — 誰が、何を知っているか

色は「主体」を表す。主体が変わるたびに、見えている情報の範囲（scope）が一段狭くなる。

Cargo — ワークスペース全クレートの依存グラフを知る唯一の主体 rustc — 1回の呼び出しにつき1クレートのみ LLVM — 1 CGU（モジュール×ジェネリック性で分割）のみ Nim — 別エコシステム、独立プロセス リンカ／リンカドライバ — 全 .o が揃って初めて着手

01樹形図 — 実行ファイルから素材まで遡る

上から下へ「誰が何を分割したか」の階層。alopex-cli 実行ファイルは、 ワークスペースの5クレート（実測ビルドログで確認した依存順）が、それぞれ複数の CGU に分割され、 各 CGU が独立した .o になったものの集合として初めてリンクされる。

枝分かれは「分割する主体」が変わる瞬間だけを表示している（rustc→CGU、Nim→gcc は分割の主体交代の一例）。 実際の CGU 数はクレートごとに -C codegen-units（既定16／インクリメンタル256）が上限で、 モジュール×ジェネリック性で仮分割した後インライン化重複が多い順に統合される（実装コード rustc_monomorphize/src/partitioning.rs で確認済み）。

03この一例から読み取れること

全体を知るのは Cargo だけ

依存グラフ（どのクレートがどの順で必要か）を把握しているのは Cargo のみ。rustc は1回の呼び出しで1クレートしか見えず、他クレートが自分のシンボルをどう使うかを知る手段がない。

実測: base.rs codegen_crate は crate 単位でしか呼ばれない

CGU 分割も局所的

LLVM に渡す単位（CGU）は、そのクレート自身のモジュール構造とジェネリック実体化だけで決まる。リンク時に実際どのシンボルが要るかは一切考慮されない。

実装コード: rustc_monomorphize/src/partitioning.rs

フロント／バックエンドは五月雨式だが無制限ではない

CGU が1個できるたびに即座にLLVMワーカーへ渡されるが、メモリ消費を抑えるため、キューが十分溜まるとフロントエンドは意図的にブロックされる。

実装コード: back/write.rs のコーディネータ設計コメント

最終リンクだけは全部揃うまで動けない

rustc も LLVM も並列化・五月雨式処理を工夫しているが、最後の1本の実行ファイルに合流する瞬間だけは、全クレートの全 .o／.rlib／外部 .a が出揃うまで待つ直列の壁が残る。

実測: mold 差し替えでも有意な速度差なし（alopexDB 実測 122.78s→124.71s）
