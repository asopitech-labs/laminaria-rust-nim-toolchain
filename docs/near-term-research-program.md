# LAMINARIA Project Progression and Near-Term Research Goal

This is the canonical starting point for LAMINARIA documentation and task selection. The [documentation map](README.md) organizes every other document as a downstream foundation, research area, work item, guide, or historical record.

## Long-term goal

LAMINARIA ultimately owns the path from Rust and Nim source semantics through its IR, transformations, work partition/fusion, scheduler, and target generation, and uses that path to build LAMINARIA itself. Package managers may provide dependency metadata, but delegating target-source semantics, IR transformation, or code generation to existing Rust, Nim, or LLVM compilers does not satisfy this path.

## Current evidence and central uncertainty

The repository has bounded evidence for source-derived IR, owned validation/interpretation/transformation, owned WebAssembly generation, Nim planning with Rust execution, incremental discovery, demand-driven execution, identity, measurement, and reference compiler routes. These are evidence fragments, not finished subsystems.

The largest current uncertainty is whether representations derived from different source languages can be composed before an existing compiler/backend boundary and then transformed, partitioned, and generated by LAMINARIA itself.

## Near-term goal

> Compose semantic IR derived from a Rust caller and Nim callee as one computation, apply an owned cross-language transformation, execute an owned target artifact, and use the preserved semantic facts to make one explicit decision between a fused and a split boundary for that same computation.

This is not completion of a mixed-language compiler, optimization, distribution, platform coverage, or self-hosting. Support, rejection, or reformulation of the candidate architecture are all valid outcomes.

## Near-term research program

1. **G1 — semantic composition and owned vertical slice (#31; informed by #3/#25/#5).** Resolve a fixed Rust declaration to a Nim definition, preserve provenance, apply one cross-language transformation, agree across the owned interpreter and owned WebAssembly, and reject one signature mismatch. Stop at an architectural conclusion.
2. **G2 — fused/split boundary decision (#25; related #13/#29 and only the required parts of #4/#7).** Compare the same workload with a fused semantic transformation and an explicit retained boundary. Decide using semantic requirements, legality, provenance, invalidation/recomputation units, artifacts, and explainability—not a broad performance contest.
3. **G3 — input-form falsification (#26; related #28/#3/#5).** Apply the selected owned path to minimal Rust-only, Nim-only, and mixed fixtures without single-language fallback to existing compilers.

G1–G3 are the current milestone. If G1 rejects the present IR hypothesis, reformulate it in #25 before proceeding to G2/G3.

## Progression after the current milestone

1. Expand semantic pressure one counterexample at a time (#32–#34, #37, #42, #44).
2. Derive work decomposition and execution architecture from real owned compiler work (#6–#8, #12, #13, #27, #36).
3. Test physical placement, persistence, and heterogeneous nodes only after logical boundaries exist (#38–#41, with required constraints fed back to #6/#7).
4. Expand surviving source/dependency coverage toward stage0→stage1→stage2 self-hosting (#2).

Measurement, identity, diagnostics, toolchain profiles, CI, platform coverage, UX, and baseline studies are supporting tracks. Activate them only where a core experiment's conclusion could otherwise be invalid.

## Task-selection rule

Fix the current goal and decision gate first; select its largest uncertainty; define the smallest positive and negative experiment that can falsify it; minimize substitutable engineering; stop when the decision is possible; then update the architecture and next goal.

The current next task is therefore G1's first experiment, not because #31 is next numerically, but because it directly tests the largest uncertainty in the near-term program.
