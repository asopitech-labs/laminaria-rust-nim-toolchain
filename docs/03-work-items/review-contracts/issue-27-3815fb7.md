## 3. 作業者が提出する成果物

提出単位は次の3種類に固定する。

1. `submission.json`: 下記の項目別索引。
2. `raw/`: 既存runner出力・診断・観測記録の原本。取得元が保持されているCIログなら、その正確なURLと位置で代用可。
3. `patches/serialize-dispatch.patch`: C03で実際に適用した変更。未保存なら未提出として扱い、推測で再作成しない。

### submission.json の固定形式

```json
{
  "contract_id": "issue27-3815fb7-review-v1",
  "subject_commit": "3815fb79048c986e25f02230bf65407e2e429c89",
  "items": [
    {
      "id": "C01",
      "availability": "present",
      "code_refs": [],
      "execution": null,
      "evidence_refs": [],
      "missing": []
    },
    {
      "id": "C02",
      "availability": "missing",
      "code_refs": [],
      "execution": null,
      "evidence_refs": [],
      "missing": ["既存記録から提出できない項目を列挙する"]
    },
    {
      "id": "C03",
      "availability": "missing",
      "code_refs": [],
      "execution": null,
      "evidence_refs": [],
      "missing": ["既存記録から提出できない項目を列挙する"]
    }
  ]
}
```

これは記入用の形式であり、上記のavailabilityは現在の採否を意味しない。
全項目を必ず含め、availabilityは `present / partial / missing` のいずれかとする。

各フィールドの内容を次に固定する。

- `code_refs`: `path, symbol, lines, assertion_or_type` を持つ配列。対象コミット上の位置と実際の式・型を記載する。
- `execution`: C02/C03で証拠がある場合、`origin, run_id, attempt, job, command, test_full_name, environment, implementation, runner_outcome` を持つオブジェクト。
- `origin`: CIのrun URL、または保存済みローカル実行記録の所在。CIとローカル記録を区別する。
- `implementation`: `normal` または `serialized-control`。後者には実適用パッチの参照を付ける。
- `runner_outcome`: runnerが記録した `passed / failed / skipped / not-run`。作業者の合否判断ではない。
- `evidence_refs`: `source, locator, supports` を持つ配列。原本の所在、ログ行・イベント位置、その箇所で確認できる事実を記載する。
- `missing`: 未記録・未保存・出所不明の内容を列挙する。空欄を推測で埋めない。

## 4. 指示者の検収手順

1. 契約ID・対象コミット・C01〜C03の過不足を確認する。
2. 指定コードを読み、型・計測境界・assertionが上記の条件を検証するものか確認する。
3. 実行元のrun/job/attemptと原本を開き、対象テストが選択され、実際に実行されたことを確認する。スイート全体の成功や対象0件は代用にならない。
4. 実行に使ったソース・ビルド・実行・ログ収集が同じ実行記録に結び付いていることを確認する。任意のログにコミット名を添えた自己申告だけでは受け入れない。
5. C03については通常実装とパッチ適用後を区別し、失敗原因が指定のassertionであることを確認する。
6. 原本で確定できないものは「証拠不足」とし、作業者の説明だけで合格にしない。ハッシュは改変・取り違え検知の補助であり、テストへの帰属や検証内容の妥当性の証明ではない。

指示者が返す判定は、各IDについて次の3つに固定する。

- `accepted`: 条件を満たす根拠の位置を併記する。
- `rejected`: 条件に反する事実と修正対象を併記する。
- `insufficient_evidence`: 足りない証拠を特定する。実装不良とは区別し、自動的な再テスト指示にはしない。

本契約は提出・検収の定義であり、新しい言語機能や資源管理の実装を今回の修正確認へ追加しない。
