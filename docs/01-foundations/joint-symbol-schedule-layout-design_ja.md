# LAMINARIA 全体設計 — なぜ「一つの計算システム」でなければならないか

## この文書の位置付け

[独自コンパイラの責務契約](compiler-ownership-contract_ja.md)が「LAMINARIAは何を所有しなければならないか」を定義し、[研究プログラム](research-program_ja.md)が「その所有をどの順序で検証していくか」を定義するのに対し、本書は両者の間にあった空白 — **なぜ既存ツールチェーンの構成では所有できないのか、何を1つの問題として同時に解く必要があるのか** — を、このセッションで得た実測・裏取り済みの証拠から埋める。

出発点は次の一言に要約できる:

> 既存ツールチェーンは「全体を知る主体」と「実際に計算する主体」を分離しており、この分離自体が構造的な性能・最適性の天井になっている。

以下、この主張を(1) 既存ツールチェーンの実装コードから裏取りし、(2) mold・LLVM・Craneliftという3つの現存する「解決の試み」がなぜこの天井を超えられないかを示し、(3) LAMINARIAが同時に解くべき問題を明示し、(4) その問題に対する現時点の仮説設計(`unified-symbol-graph`実験)を示す。

## 1. 観測された分離: 「全体を知る主体」と「計算する主体」は別人格である

このセッションで、実装コードを直接読んで裏取りした事実は次の通りである。

### 1.1 Cargoは全体を知っているが、計算しない

`cargo`本体のソース(`src/cargo/core/compiler/job_queue/dependency_queue.rs`、issue #59・#66で裏取り)を読むと、`DependencyQueue`は次を行う:

- `queue_finished`: 各ノードについて `cost[n] + Σ cost[transitive dependents of n]` を計算する。これは「このノードが完了しないと、どれだけ下流の作業がブロックされ続けるか」というクリティカルパス上の重みである。
- `dequeue`: 依存が0件になった候補のうち、その重みが最大のものを選ぶ(`max_by_key`)。

つまりCargoは**ビルドグラフ全体を知っており、クリティカルパスを意識した実装済みのスケジューラを持つ**。「準備できたものから適当に並列実行する」という単純化された想定は誤りだった(issue #59で当初立てていた仮説を、実装コードを読んで訂正した)。

しかしCargoは**一切のコード生成・最適化・リンクを行わない**。それらはすべて`rustc`/`nim`/`cc`という別プロセスへ委譲される。Cargoは「誰が何をいつ着手すべきか」を知っているが、「何が生成されるか」には関与しない。

### 1.2 rustcは計算するが、全体を知らない

`rustc`のCGU(codegen unit)分割ロジック(`compiler/rustc_monomorphize/src/partitioning.rs`、issue #48で裏取り)を読むと:

- `place_mono_items`は、モノモーフィ化済みの各アイテムを、そのアイテムが属する**ソースレベルの`mod`**を基準にCGUへ割り当てる。1モジュールにつき「安定」(非ジェネリック)用と「揮発」(モノモーフィ化ジェネリック)用の2つのCGUに分かれる。
- `merge_codegen_units`は、インライン化されるアイテムの重複が最大になるペアを貪欲に統合し、`-C codegen-units=N`(既定16、インクリメンタル時256)まで削減する。

この分割は**そのクレート自身のモジュール構造とジェネリック実体化だけから決まる**。「他のクレート(あるいはNimble/C/C++の領域)が、自分のどのシンボルを実際に参照するか」を一切知らず、知ろうともしない。

つまり、**全体グラフを知る主体(Cargo)はコード生成に触れず、コード生成する主体(rustc、1クレート1回起動)は全体グラフを見ない**。これは複数プロセス間の分離であるだけでなく、rustc単体の内部でも同じ分離構造が繰り返されている(CGU分割はクレート内で同じ現象のミニチュアである)。

### 1.3 リンカは両方から独立した第3の主体である

`lld`のセクション配置最適化(`lld/ELF/Writer.cpp`、`lld/ELF/CallGraphSort.cpp`、issue #59で裏取り)を読むと:

- `sortSection`/`buildSectionOrder`は、既にリンク済みの出力の中でセクション順を並べ替える。
- `computeCallGraphProfileOrder`は、実行時プロファイル(Call-Chain Clustering / Cache-Directed-Sort、データセンター向け関数配置の実論文の実装)を入力に取り、**実行時のi-TLB/i-cacheミス削減**を目的とする。
- この入力は**ビルド時にCargoが知っていたクリティカルパス情報とは完全に無関係**であり、両者は異なるデータソースから、異なる時刻に、異なるツールによって計算される。

つまり最終的な`.o`の空間配置(どのオブジェクトがどの順で最終バイナリに書き込まれるか)は、ビルド時のスケジューリング(Cargoの守備範囲)からも、コード生成(rustcの守備範囲)からも独立した**第3の、後から付け足される最適化**として存在する。

### 1.4 3者の分離は「設計ミス」ではなく歴史的必然だった

Cargo/rustcのオーケストレーション設計をこのセッションで文献調査した結果:

- npm/Bundlerを参考に2014年に設計された(`rust-lang/rfcs` Issue #610)。
- クレート境界を越えた並列コンパイルは早期に提案されたが、**LLVMコンテキストがスレッドセーフでない**という制約のために頓挫した(1クレート=1`LLVMContext`という現在の設計は、この制約への適応である)。
- RFC 1298はインクリメンタルコンパイルとwhole-program最適化のトレードオフを明示的に扱っており、「全体最適化」と「差分の速さ」は最初から両立しない要求として認識されていた。

つまりこの3分離(Cargo/rustc/リンカ)は、2014年当時のLLVMの技術的制約(スレッド非安全なコンテキスト)に対する合理的な適応として生まれたのであり、意図的に設計された最適解ではない。**制約が変われば、分離を前提としない設計も可能なはずである。**

## 2. 3つの既存の「解決の試み」がなぜ不十分か

### 2.1 mold: 下流だけを並列化しても、上流の分離は残る

mold linkerは、全入力を先に並列パースし、独立した並列パスでシンボル解決を行う設計を持つ(issue #66で実測・裏取り)。これはGNU ld由来の逐次的単一パス設計([1970年代のI/O・メモリ制約に由来](../02-research-areas/compiler/llvm-rediscovery-research_ja.md)が長く「唯一の抽象」として継承されてきた)からの明確な脱却であり、**方向性はLAMINARIAと一致する**。

しかし:

- alopexDB実測では有意な速度改善は確認できなかった(issue #66)。
- moldは**汎用リンカ**であり、コンパイラの出力(`.o`ファイル)を所与として受け取る。つまりmoldは「コンパイラが生成した後」の問題しか解いておらず、「コンパイラは何を生成すべきか」という上流の設計には踏み込まない。これはLAMINARIAの立場(コンパイラ出力そのものを再設計する)と**アプローチが逆**である。
- moldを採用してもLAMINARIAの構造的問題(節1で示した3者分離)は解消しない。mold自体は不採用とし、その設計思想(並列パース→独立解決パス)だけを`unified-symbol-graph`仮説に反映する形で継承する。

### 2.2 LLVM: 全体を知らないまま最適化する主体

LLVM内部を実測・調査した結果(`llvm-internals-observed_ja.md`):

- コード生成段階(命令選択+レジスタ割付)が実行時間の約73%を占める。
- LLVMの最適化パスは、Nikita Popov氏(LLVM開発者)自身の分析によれば限界効用逓減の性質を持ち、追加コストに見合う改善が徐々に小さくなる。
- Rustのモノモーフィ化はIR量を大きく増幅させ、これがLLVM側の処理コストをさらに押し上げる。
- ThinLTOはサマリーの直列マージ→並列バックエンド処理という構成を取るが、これは「サマリーという要約された全体情報」を経由する近似であり、真に全体グラフを見ているわけではない(2016年から存在する仕組みであり、根本的な分離構造自体は変わっていない)。

LLVMは「1クレート内でのみ全体を知る」主体であり、Cargoが持つエコシステム横断のグラフ情報とは接続されていない。節1.2で述べたCGU分割の孤立性は、この意味でLLVM側の限界でもある。

### 2.3 Cranelift: 統合自体がまだ実運用に耐えない

Cranelift backend(`rustc_codegen_cranelift`)で実際にalopex-cli(依存200超の実運用Rustクレート)をビルドしようとした結果(issue #48):

- Cranelift単体、Cranelift+mold併用のいずれも、`aws-lc-sys`のシンボル未解決でリンクに失敗した。
- 原因はCraneliftのコード生成自体ではなく、`-Zcodegen-backend`経由のバックエンド切替が、Cargoの`build-dependencies`/`dependencies`分離ビルドと絡み、同一クレートが異なるfingerprintの2ユニットとしてビルドされるという、既存ツールチェーンの構成そのものに起因する不整合だった。

この失敗は偶発的なバグではなく、**既存の3者分離構造(節1)の上に第4のバックエンドを継ぎ足そうとすると、分離の継ぎ目で整合性が壊れる**という一般的な症状の一事例である。バックエンドを差し替えるだけでは、分離構造自体の問題は解決しない。

## 3. LAMINARIAが同時に解くべき問題

以上の裏取りから導かれる帰結は明確である。既存ツールチェーンの改善(mold採用、Cranelift採用、LLVM最適化のチューニング)は、いずれも**節1で示した3者分離を前提としたまま、個々の主体を局所的に改善する**試みであり、分離そのものは解消しない。

LAMINARIAが目指すべきは、**「全体を知る主体」と「実際に計算する主体」を同一の1つの計算システムへ統合する**ことである。これは`docs/01-foundations/compiler-ownership-contract_ja.md`が既に述べている「一つの計算システムとして扱う」という原則の、このセッションで得られた具体的な裏付けである。

同時に解くべき問題は、少なくとも次の3つに整理できる。これらは**別々の最適化問題として逐次解いてよいものではない**。

### 問題A: エコシステム横断のシンボル解決

Cargo/Nimble/C/C++という4つの領域(realm)にまたがる境界シンボル(FFI境界を越えるシンボルのみ。領域内部のシンボルは対象外)を、事後的な「リンク」パスとしてではなく、各領域のフロントエンドが局所的な意味解析を行っている**最中に**解決できるようにする。

### 問題B: スケジューリング(いつ着手するか)

Cargoの`DependencyQueue`が既に実装しているクリティカルパス優先スケジューリングに相当する機能。「どのシンボルの生成が、どれだけ多くの下流作業をブロックしているか」を把握し、着手順序を決める。

### 問題C: 空間配置(どこに書き込むか)

lldの`CallGraphSort`が実装している実行時ロケーリティ最適化に相当する機能。「どのシンボル同士が頻繁に相互参照するか」(`RequiresEdge`が既に記録している情報)を使い、最終イメージ内での配置順を決める。

### 問題B×Cは分離できない — これがこのセッションの核心的発見

ユーザーからの強い指摘により訂正された点: 「最終実行バイナリ内の`.o`の順番は先に予測できないか」という問いへの正確な答えは、**「既定では入力順で完全に決定的だが、決定的なアルゴリズムで再配置する複数の明示的な仕組みがある」**というものであり、かつ、その配置(空間)とスケジュール(着手順序)は**独立に最適化してよい2つの問題ではない**。

タスクスケジューリングとデータ配置の同時最適化(makespanとロケーリティを同時に最小化する問題)は、スケジューリング理論において**既知のNP困難クラス**であることを文献調査で確認した(issue #59)。Cargoとlldが、それぞれ単独では十分に洗練された実装でありながら、この2つを別々の・盲目的な(互いの情報を参照しない)パスとして解いているのは、既知の困難な結合問題を意図的にか歴史的経緯でか2つの単純な問題へ分解した結果であり、この分解自体がLAMINARIAにとっての改善対象である。

`unified-symbol-graph`仮説の`SharedSymbolGraph`は、この結合問題を1つの構造で解くための最小限のデータを既に持っている:

- `mutation_seq`(各宣言がいつ到着したか)は、ビルド時クリティカルパス位置の安価な代理指標になり得る。
- `RequiresEdge`(どのシンボルがどのシンボルを最も頻繁に参照するか)は、コールグラフプロファイルと同じ形の情報を既に記録している。

`assign_layout`が現状、決定性のためだけに`SymbolId`のソート順で配置している(`experiments/unified-symbol-graph/src/lib.rs`の該当コード参照)のは、この2つの信号を使っていない**未解決の設計課題**として明記されている。これを両方使う配置関数を実装することが、問題B×Cを1つの問題として解く最初の具体的なステップになる。

## 4. 現時点の仮説アーキテクチャ: `unified-symbol-graph`

上記の問題A(エコシステム横断解決)に対する最小実装が、worktree `experiments/unified-symbol-graph/`に存在する。要点:

- **4つの領域の分散グラフであり、単一のモノリシックなテーブルではない**(ユーザーの明示的な指示による設計選択)。各領域(Cargo/Rust、Nimble/Nim、C、C++)は自分の内部型情報・シグネチャの詳細を一切外部へ露出しない。
- **境界を越えるシンボルだけ**が共有グラフのノードになる。領域内部のシンボルは対象外。これにより共有・競合する状態を最小化しつつ、各領域の重い意味解析(パース、型検査、モノモーフィ化)は完全にローカル・並列のまま保たれる — moldが「全入力を並列パース→独立した並列パスで解決」という形で対GNU ld/lld比で取った構造を、**オブジェクトファイルの1層上流に適用する**形になっている。
- コンパイラの出力は「アドレスだけの主張」ではなく、実際の機械語バイト列(`CodeBody`)と、その中の未解決参照箇所(`ElfX86_64PendingReloc`)をセットで持つ。これは実際の`cc -c`出力を`objdump`で直接観測し、`R_X86_64_PLT32`の実バイト列を裏取りした上で設計されている。
- プラットフォーム非依存の共通型は**意図的に採用していない**。ELF/x86_64、COFF(Windows)、Mach-O(macOS ARM64)、WASMという4つの再配置モデルは、実測(ELF・COFF・WASM)と一次文献(ARM64 Mach-O)によって構造的に異なることが確認されており、それぞれ独立した型として設計する方針を取る。共通化してよいのは「共有グラフが事後リンクパスを置き換える」という**原理**だけであり、`ElfX86_64PendingReloc`のような**具体的な型は共通化しない**。

この仮説はissue #66・#48・#59に段階的に記録されており、worktree `worktree-unified-symbol-graph-hypothesis`のコミット履歴(`9ae2b40`から`aa56783`まで)が検証過程そのものの記録になっている。

## 5. まだ解けていないこと(次の設計課題)

- `assign_layout`を、`mutation_seq`と`RequiresEdge`の両方を使う結合最適化関数へ置き換える具体的なアルゴリズムはまだ実装されていない(節3で述べた通り、設計課題として明記されているのみ)。
- ARM64(Mach-O/ELF双方)、Windows COFF(MSVC ABI)は、リロケーション適用関数がまだ実装されていない(文献調査は完了、実機検証は未実施)。
- 問題A(境界シンボル解決)は実験レベルで動作確認済みだが、問題B×C(スケジュール×配置の結合最適化)はまだアルゴリズムの実装に着手していない。
- Craneliftの実測失敗(節2.3)が示す「既存分離構造への継ぎ足しは整合性が壊れる」という一般則が、LAMINARIA自身の設計(Rust/Nimランタイムスケジューラ+Nimプランニングカーネルという2言語構成)にも当てはまらないことを、今後LAMINARIA自身の実装が育つ過程で継続的に検証する必要がある。
